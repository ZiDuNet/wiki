# 代码仓库知识图谱

**类型:** 概念

## 定义

把代码仓库编译成结构化知识图谱，抽取依赖、调用链、cluster 和 execution flow，让 AI 编程工具不再临时 grep，而是拥有一张仓库地图。

## 核心问题

传统 AI 编程助手的问题：每次都从文件树里盲搜，漏掉跨文件关系、隐式依赖、调用链和修改影响面。一个 validateUser 的返回值改了，真正重要的不是它当前文件怎么写，而是谁调用它、哪些流程依赖它、哪些测试会被影响。

这些问题天然适合图，不适合只靠片段召回。

## 技术路线

### Tree-sitter 静态解析 + LLM 语义理解

两步分开，结果更可靠：
1. AST 派生确定性图谱（覆盖率、成本、多跳 grounding）
2. LLM 语义补充（跨文件关系理解）

### 对比三条路线

|| 路线 | 特点 |
|-----|------|
| 纯向量检索 | 擅长找主题相似片段，多跳架构推理容易断 |
| LLM 生成知识图谱 | 语义理解能力强，但成本高、覆盖不稳定 |
| AST 派生确定性图谱 | 覆盖率、成本和多跳 grounding 更可靠 |

## 与 Karpathy LLM Wiki 的呼应

|| 对象 | Karpathy LLM Wiki | 代码仓库知识图谱 |
|-----|-------------------|------------------|
| 面向对象 | 论文、笔记、网页、材料 | 函数、类、依赖、调用链、执行流 |
| 机制 | 把知识沉淀成持续维护的 wiki | 把仓库沉淀成持续查询的结构图 |

共同点：把"临时上下文"变成"持久结构"。

## 工具形态

不是只给一个"搜索代码"的接口，而是提供结构化工具：

|| 工具 | 解决的问题 |
|-----|-----------|
| query | 怎么找 |
| context | 一个符号的上下游关系 |
| impact | 改它会影响谁 |
| detect_changes | 当前 diff 会波及哪些流程 |
| rename | 重命名这种跨文件操作 |
| cypher | 底层图查询能力 |

搜索返回候选文件，图谱返回结构关系。前者让 agent 自己继续猜，后者把"应该看哪些关系"提前算好。

## 论文支撑

### Codebase-Memory

基于 Tree-sitter 的持久知识图谱，通过 MCP 给 LLM coding agent 使用。31 个真实仓库对比：
- 回答质量接近传统文件探索 agent
- token 消耗低一个数量级
- 工具调用明显减少

### Reliable Graph-RAG for Codebases

结论：基于 AST 的确定性图在覆盖率、成本和多跳 grounding 上更可靠。

## 应用场景

- 多模块、多服务、多 agent 协作的代码仓库
- 需要理解修改影响面的重构工作
- 新人入职快速理解代码结构
- 大规模代码库的 AI 编程助手
