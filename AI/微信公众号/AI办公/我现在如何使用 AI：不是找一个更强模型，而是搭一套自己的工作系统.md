# **引子：这篇 V2EX 帖子真正有价值的地方**

这两天在 V2EX 看到一篇关于 AI 提效 Harness 的帖子，作者分享了自己如何把 Codex App、模型、Skills、提示技巧、编辑器、终端和任务管理方式串起来，用 AI 辅助日常开发。

这篇帖子最打动我的，不是某个工具，也不是某个 Prompt，而是一个很关键的判断：AI 提效的核心，已经不再是“问 AI 一个问题”，而是“把 AI 纳入自己的工作流程”。

这和我最近半年来的体验非常接近。过去很多人用 AI，是把它当成一个更聪明的搜索框、写作助手、代码生成器。遇到问题，打开聊天框，问一句，复制结果，再自己试。

但真正用深以后会发现，这种方式很快会遇到瓶颈。AI 并不是不会写，而是不知道边界；不是不会回答，而是不知道业务语境；不是能力不够，而是没有被放进一个稳定、可验证、可复用的工作系统里。

# **一、我对 AI 的使用方式，已经发生了变化**

刚开始用 AI 的时候，我也会追求三个东西：哪个模型更强？哪个工具更火？哪个 Prompt 更神？

后来发现，这些当然重要，但都不是最核心的。因为模型会变，工具会换，Prompt 也会失效。真正长期有效的，是一套属于自己的工作方法：什么任务交给 AI，什么任务必须自己判断；哪些事情可以自动化，哪些地方一定要人工把关；AI 输出以后，怎么验证，怎么沉淀，怎么进入下一次复用。

Anthropic 在《Building Effective Agents》中把增强型 LLM、workflow 和更自主的 agent 区分开来，强调应从简单、可组合的工作流逐步增加复杂度。这一点很重要：不要一上来就追求“全自动”，很多真实场景里，稳定 workflow 反而更可靠。

我的感受更直白一点：AI 不应该先被神化，而应该先被工程化。

# **二、我现在使用 AI，主要分成五层**

如果用一张图来描述，我现在的 AI 使用方式大概是五层：模型层、规则层、Skills 层、工具层、复盘层。

模型层负责能力上限；规则层负责边界和习惯；Skills 层负责固定工作流；工具层负责执行环境；复盘层负责持续进化。

很多人只关注第一层，也就是模型。今天用 GPT，明天用 Claude，后天用 Gemini，再换 Codex、Cursor、Claude Code、OpenCode。工具越试越多，但自己的流程没有沉淀下来，最后反而更乱。

我的判断是：模型决定上限，流程决定下限。上限很重要，但下限更关键。尤其在企业场景里，不能只看 AI 偶尔给出一个惊艳答案，而要看它能不能稳定、可控、可复用地完成任务。

|  |  |  |
| --- | --- | --- |
| **层级** | **解决的问题** | **我的使用原则** |
| 模型层 | 能力上限 | 按任务路由，不迷信单一模型 |
| 规则层 | 边界与约束 | 先写禁止操作和交付标准 |
| Skills 层 | 重复工作流 | 少而精，每个 Skill 解决一个明确问题 |
| 工具层 | 执行环境 | 代码、写作、验证、沉淀分工清楚 |
| 复盘层 | 持续进化 | 把反复提醒写进规则和模板 |

# **三、模型不是信仰，而是任务路由**

我现在不会再纠结“到底哪个模型最好”。更实际的做法是：按任务类型选择模型。

写作、改稿、观点提炼，我更看重语言风格、结构能力和表达张力；代码、多文件修改、测试修复，我更看重上下文理解、工程执行和工具调用能力；复杂方案、技术选型、架构分析，我更看重推理深度和反驳能力；企业材料、汇报稿、制度解读，我更看重稳妥、口径一致和可控表达。

OpenAI 在 Agent 实践指南中强调，模型选择应先建立评估基线，优先满足准确性目标，再在可能时用较小模型优化成本和延迟。这不是“越大越好”的逻辑，而是任务路由的逻辑。

我的做法很简单：重要任务，用最强模型；低风险任务，用更快模型；代码任务，用适合工程执行的工具型模型；正式材料，必须经过二次审校；涉及企业数据、业务口径、财务结论，不能只信模型，要有验证链路。

# **四、规则层：让 AI 先知道什么不能做**

我现在越来越重视规则文件，比如 AGENTS.md、CLAUDE.md、项目说明文档、运行手册、设计规范、验收标准。

OpenAI 的 Codex 文档明确提到，Codex 会在开始工作前读取 AGENTS.md，通过全局指导和项目级覆盖，让每个仓库都有一致的工作预期。AGENTS.md 这个开放格式，也可以理解成“给 coding agent 看的 README”。

我自己的经验是，规则文件不要一上来写得很复杂。最开始只写三类就够了：常用命令、禁止操作、交付标准。

比如在企业项目里，我会特别强调：不要随意重构无关代码；不要覆盖用户已有改动；不要执行数据库写操作，除非明确授权；涉及财务口径、指标口径、权限边界，必须说明依据；涉及生产部署、镜像推送、配置变更，必须先解释影响范围；所有修改完成后，要给出变更摘要、验证结果和遗留风险。

这不是形式主义。这是把 AI 从“会干活”变成“按规矩干活”。

# **五、Skills 的本质，不是插件，而是经验封装**

这次 V2EX 帖子里最值得看的部分，是作者对 Skills 的整理。我也有类似感受：Skill 不应该理解成一个炫技插件，而应该理解成一种固定工作流。

比如，做方案前，先调研、拆解、反驳、再生成；修 Bug 时，先定位根因，再改代码，不要一上来乱试；交付前，先检查 diff、测试结果、边界情况；写文章时，先确定观点，再搭结构，再润色语言；做页面时，先确定设计目标，再做视觉系统，而不是直接堆组件。

Skill 真正有价值的地方，是把你反复要求 AI 做的动作固化下来。

这里有个判断我非常认同：不要安装太多 Skill。工具很多不等于流程成熟。很多人一看到 Skill，就想全装。写作、设计、调研、代码、PR、浏览器、文档、测试、部署，一口气装几十个，最后自己记不住，AI 也不知道该用哪个。

我的建议是，普通人先保留 6 到 10 个高频 Skill 就够了。真正重要的不是 Skill 数量，而是每个 Skill 是否解决一个明确问题。

# **六、我在企业 AI 项目里，最看重“可验证”**

如果只是个人写点代码、做个小工具，AI 输出错了，大不了回滚。但企业项目不一样。

尤其是财务数智化、资产管理、智能问数、管理报告这类场景，AI 不能只追求“看起来聪明”。它必须可验证。

比如我做财务智能助手、智能问数和管理报告相关工作时，会特别关注几个问题：它引用的制度来源是什么？它生成的指标口径是否一致？它有没有越权访问数据？它生成 SQL 的表、字段、粒度是否正确？它有没有把预算、核算、资金、资产这些概念混用？它能不能解释结论，而不是只给一个答案？

这其实和 Agent 工程里的很多原则是相通的。HumanLayer 的 12-Factor Agents 强调拥有自己的提示词、上下文窗口、控制流，以及将错误压缩回上下文窗口等原则，本质上都是为了提高可靠性和可控性。

我的理解更业务化一点：企业 AI 的核心不是生成，而是生成之后能不能被信任。

# **七、工具链不必统一，但分工要清楚**

我现在不会试图用一个工具解决所有问题。更现实的方式是分工。

Codex、Claude Code、Cursor、OpenCode 这类工具，更适合进入代码仓库，做多文件修改、解释架构、修 Bug、生成测试、写文档。ChatGPT、Claude、Gemini 更适合做方案推演、文章写作、结构化分析、汇报材料打磨。Zed、VS Code、Cursor 更适合最后看 diff、做精修和人工确认。浏览器 Agent 或 computer use 更适合做页面真实验证、点击、截图、检查交互。知识库、笔记软件、项目文档，则负责长期沉淀。

这背后的关键不是“哪个工具最好”，而是：每个工具在你的工作流里负责什么。工具没有角色，就会互相打架。工具有了角色，才会形成系统。

# **八、我现在给 AI 任务，会更像给团队成员布置任务**

过去我会这样问：帮我写一篇关于 AI 的文章。

现在我会这样给任务：这篇文章面向公众号读者；主题是我如何使用 AI；不要写成工具清单，要写成方法论和真实经验；核心观点是 AI 提效的关键不是 Prompt，而是工作系统；读者包括企业项目经理、产品经理、技术负责人和 AI 爱好者；文章要有判断，不要堆概念；要结合企业落地、财务数智化、代码工具链和个人效率；最后给出一套可执行建议。

这就是提示技巧的本质。不是神奇咒语，而是把目标、上下文、边界、标准讲清楚。很多时候 AI 表现不好，不是模型不行，而是任务定义太模糊。

你给它一句口号，它只能给你一篇口号文；你给它一个清晰任务，它才可能给你一个可用结果。

# **九、我对 AI 的一个新判断：个人也需要“上下文工程”**

过去讲上下文工程，更多是面向系统开发。但现在我觉得，个人也需要上下文工程。

也就是说，你要有意识地管理 AI 能看到什么、记住什么、遵守什么、复用什么。个人偏好放到全局规则里，项目结构放到项目规则里，业务口径放到知识库里，常用任务沉淀成 Skill，反复踩坑写进注意事项，成熟流程固化成模板，阶段成果整理成文档。

这件事一开始会觉得麻烦。但只要坚持几周，效果会非常明显。因为你不再需要每次从零解释，AI 也不再像一个临时外包，而更像一个逐渐熟悉你工作方式的协作者。

# **十、从一个最小 Harness 开始**

如果你也想开始搭自己的 AI 工作系统，不建议一上来搞得很复杂。可以从四个文件开始：一个全局规则文件、一个项目规则文件、一个任务模板、一个复盘文档。

全局规则文件，写长期偏好和安全边界；项目规则文件，写项目结构、命令、测试方式和修改约束；任务模板，写清楚背景、目标、输入、输出、限制、验收标准；复盘文档，记录 AI 经常犯的错、你反复提醒的话、值得复用的流程。

然后每周问自己四个问题：哪些话我反复对 AI 说？哪些地方 AI 经常跑偏？哪些输出我总要手动重改？哪些流程可以沉淀成规则或 Skill？

这就是个人 AI Harness 的起点。不炫，但有效。

# **结语：AI 不是外挂，而是新的工作操作系统**

我越来越觉得，未来真正会用 AI 的人，不是最会问问题的人，而是最会设计工作流的人。

AI 不只是一个聊天框。它正在变成一种新的工作界面。它可以写代码、查资料、做方案、生成文档、分析数据、设计页面、辅助决策。

但前提是，你要给它规则、上下文、工具和验收标准。没有这些，AI 就只是一个很强的回答机器；有了这些，AI 才会变成你工作系统的一部分。

所以，今天我想分享的不是“某个模型多强”，也不是“某个工具多好用”。而是一个更朴素的经验：别只收藏 Prompt，开始搭建自己的 AI 工作系统。

这件事越早做，复利越明显。
