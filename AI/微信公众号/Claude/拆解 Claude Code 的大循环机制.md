如果只把终端 Agent 看作一个“会调用工具的聊天框”，就会把它简化成一次问答。用户输入一句话，模型读文件、改代码、跑测试，最后给出结果。这个表面体验很顺，背后支撑它的是一个长时间运行、持续决策的循环系统。

Claude Code 的核心是一套持续推进的 Agentic Loop：模型判断当前状态，发起工具调用，运行时执行动作，把结果重新喂回模型，再进入下一轮判断。复杂任务能跑几十轮，靠的是循环本身对上下文增长、权限拦截、工具失败、API 限流和用户中断的承载能力。

这套机制把错误也纳入了循环。文件不存在、命令失败、权限被拒绝、API 短暂不可用，这些异常不会天然等于 CLI 崩溃。它们会被截住、归类、转译成模型和 UI 都能理解的反馈，让下一轮决策可以继续发生。

Claude Code 的大循环可以拆成四层：QueryEngine 负责推进 turn，Tool System 负责执行动作，Permission / Hook 负责拦截边界，React + Ink 负责把状态变化渲染成终端体验。

数据流可以压缩成一句话：收集现状 -> 模型决策 -> 执行动作 -> 验证结果。错误处理和 UI 渲染像两条并行线，贯穿整个循环，分别处理韧性和交互性。

## 一、大循环把复杂任务拆成连续 turn

Agentic Loop 的基本单元是 turn。每个 turn 里，模型根据当前上下文生成回复；回复里可能包含自然语言，也可能包含一个或多个工具调用；运行时执行工具，再把工具结果作为下一轮输入送回模型。

这就形成了一个稳定循环：收到 prompt，构造上下文，模型判断，执行工具，返回结果，继续判断。直到模型给出不再包含工具调用的文本回复，循环才进入收尾阶段，产出最终结果、token 用量、成本和 session ID。

复杂工程任务正是靠这种 turn 累积完成的。第一轮可能只是在仓库里搜索文件，第二轮读取关键模块，第三轮修改代码，第四轮运行测试，第五轮根据测试失败继续修复。模型没有一次性猜完整答案，而是在每个回合用真实执行结果校正下一步。

如果它试图一次性完成整条链路，很容易因为项目结构、测试入口或依赖关系的错误假设而失败。循环的价值在于把文件系统、编译器、测试框架和权限系统返回的“硬事实”接回来，用反馈不断收缩下一步动作的范围。

一个 turn 里发生的三件事

1. **模型决策：** 在 system prompt、工具定义、会话历史和项目上下文里判断下一步。

2. **运行时执行：** 工具系统校验参数、经过权限层，再执行文件、搜索、命令或子 Agent 操作。

3. **结果回流：** 工具输出、错误、拒绝原因和状态事件被包装成消息，进入下一轮上下文。

## 二、Gather Context 是每一轮决策的地基

Claude Code 的循环建立在完整上下文之上。每一轮请求都会带上系统提示词、工具定义、会话历史、项目规则、技能描述和必要的上下文文件。模型看到的是一个被运行时整理过的任务现场，远比用户刚刚敲下的一句话更完整。

上下文在同一个 session 内持续累积。读过的文件、执行过的命令、工具返回的输出、模型已经做过的判断，都会影响后续 turn。长会话接近窗口上限时，系统会触发压缩，把旧历史折叠成摘要，保留近期动作和关键决策。

Gather Context 的意义在于让模型贴着“当前工程事实”工作。它既包括静态上下文，比如 `CLAUDE.md` 和工具 schema；也包括动态上下文，比如刚刚失败的测试输出、刚读到的函数实现、刚被拒绝的危险命令。

## 三、Take Action 由工具系统和权限层共同完成

模型只能提出动作意图，实际执行动作的是工具系统。Claude Code 的工具带有名称、输入 schema、权限声明、执行函数和结果格式。运行时根据工具名找到实现，校验输入，再决定能不能执行。

权限层把这个循环变成可控系统。读文件、搜索代码、写文件、跑命令、访问外部服务，风险等级完全不同。Claude Code 会在工具执行前检查 allow / deny 规则、permission mode 和 hook 回调；被拒绝的工具调用不会直接消失，而是变成一条拒绝结果回到模型手里。

这种安全设计对模型是透明的，也是可理解的。模型不需要内化完整的安全策略，只需要像处理“文件不存在”一样，处理“权限被拒绝”这个结果，再调整下一步动作。模型能力和安全策略因此被拆开：模型负责规划，运行时负责守边界。

模型能避开“黑箱失败”式猜测，直接看到“这个 Bash 命令未获批准”“这个工具被策略拦截”“这个目录不可访问”。下一轮它可以改用只读工具、缩小命令范围、请求用户授权，或者说明任务无法继续。

| 动作入口 | 运行时处理 | 反馈给模型 |
| --- | --- | --- |
| Read / Glob / Grep | 校验路径和参数，读取项目事实。 | 文件内容、匹配列表、空结果或读取错误。 |
| Edit / Write | 经过编辑权限和文件差异校验。 | 写入成功、冲突、格式失败或拒绝原因。 |
| Bash | 匹配命令规则，执行并捕获退出码。 | stdout、stderr、exit code、超时和权限结果。 |
| Agent / Skill | 启动独立上下文的子任务。 | 子 Agent 摘要，过滤完整子会话里的过程噪声。 |

## 四、Verify Results 让循环具备自我校正能力

Agent 的可靠性来自执行后的验证反馈。工具结果回到模型时，模型看到的是具体证据：测试输出、命令退出码、文件 diff、搜索结果、工具错误、权限拒绝、API 重试事件。

这让 Claude Code 的循环更接近一个工程状态机。每次工具调用都会把系统推进到新的状态：文件已修改、测试未通过、权限被拒绝、上下文已压缩、预算已接近上限。下一轮模型会在这个状态上继续工作。

验证并不总是单独的测试步骤。读文件验证假设、跑命令验证变更、搜索验证影响范围、用 hook 校验危险动作，本质上都是 Verify Results。它们把模型输出从“文本建议”拉回到“可观察事实”。

## 五、异常拦截转译是生产级 Agent 的分水岭

普通脚本遇到异常，最自然的路径是抛错、打印堆栈、退出进程。Agent CLI 不能这么脆弱。因为工具失败本身就是任务信息的一部分：文件不存在说明搜索范围错了，测试失败说明补丁不完整，权限拒绝说明动作越界，API 限流说明需要等待或收束任务。

Claude Code 的错误处理思路，是把底层错误尽量留在循环里。工具执行失败会被包装成工具结果；权限拒绝会被包装成拒绝消息；API 短暂错误会进入 retry 逻辑；超过 turn 或预算限制会生成带 subtype 的 ResultMessage。无法恢复的执行中断，才以错误结束 session。

演示级 Agent 遇到 `ENOENT`，常见结果是崩溃，或者只给出一句“我遇到了一个错误”。生产级 Agent 会把 `ENOENT` 转译成“你尝试读取的文件不存在，请检查路径是否正确”，再把这条结构化信息放回上下文，驱动模型进入下一轮“修正路径”的决策。

这相当于给模型建立了一套错误语言。操作系统说的是 `ENOENT`、`EACCES`、非零退出码、连接重置、429、529；Agent 循环需要转成“路径不存在”“权限不足”“命令失败”“正在重试”“预算耗尽”。模型理解后，才有机会选择下一步。

```
tool_call: Bash("npm test")runtime:  exit_code: 1  stderr: "AuthService should reject expired token..."loop feedback:  type: "tool_result"  translation: "exit_code + stderr -> 可读的失败摘要"  content: "测试失败，失败用例和堆栈如下..."next turn:  model reads failure -> opens auth.ts -> edits condition -> reruns tests
```

错误处理的四种出口

1. **可继续错误：** 工具返回失败结果，模型在下一轮改策略。

2. **可等待错误：** API 限流、连接错误进入 retry，并把等待状态暴露出来。

3. **可解释终止：** 命中 max turns、预算或结构化输出重试上限，ResultMessage 给出 subtype。

4. **不可恢复中断：** 请求取消、运行时崩溃或未处理异常，session 以 execution error 收尾。

这条工程取舍很清晰：能转译成反馈的错误，就不要急着炸掉进程。生产级 Agent 的韧性来自错误后的结构化证据，循环可以继续，用户可以看懂，调用方也能恢复 session。

## 六、Persistent Retry 让长任务不被短暂故障打断

长时间运行的 Agent 一定会遇到外部系统波动。网络抖动、模型服务限流、OAuth 失效、网关 5xx、连接重置，都可能发生在某个 turn 里。对短请求来说，失败就返回错误；对长任务来说，过早退出会浪费前面已经完成的上下文和动作。

Persistent retry 的价值落在长任务保护上。重试逻辑会区分错误类型，处理 401/403 这类认证刷新，识别 429/529 这类限流或过载，按 retry-after 和退避策略等待。等待时间较长时，还会周期性输出系统状态，避免宿主进程误判为空闲。

它更像 Agent Loop 外围的一层生命维持机制：模型调用失败时，循环暂时停在当前状态；恢复后继续同一个 session，保留用户描述、已读文件和已经完成的验证步骤。

## 七、React / Ink 把状态机渲染成终端产品

Claude Code 的终端体验不像传统 CLI 那样打一行命令、吐一段文本。它更像一个运行在终端里的 React 应用：输入框、消息列表、权限确认、工具进度、状态栏、diff 展示、错误提示，都由状态变化驱动渲染。

AppState 承接运行时状态，React context 和 hooks 把状态分发到终端组件，Ink 负责把组件树绘制到命令行界面。这样一来，底层循环不需要直接关心“该怎样画 UI”；UI 也不需要直接执行工具。它们通过消息流和状态对象连接。

这种拆法让交互细节变得可维护。工具正在运行，UI 可以显示进度；权限等待用户确认，UI 可以切换到确认态；API 正在重试，UI 可以显示剩余等待；上下文压缩发生，UI 可以提示边界事件。复杂状态不再散落在打印语句里，而是进入统一状态层。

## 八、这套循环给 Agent 工程的启发

Claude Code 的大循环把 Agent 系统里最容易混在一起的四件事拆开了：上下文构造、动作执行、结果验证、错误转译。模型只负责在当前状态下做下一步判断；运行时负责把世界的真实反馈整理成模型能继续使用的消息。

这也是终端 Agent 和普通聊天产品的关键差异。聊天产品可以在回答里解释失败，终端 Agent 还要在失败后继续处理文件、命令、权限、预算和 UI。循环越长，错误越多，状态越复杂，工程边界就越重要。

许多自研 Agent 的瓶颈就在这里：它们能调用工具，但工具结果回流不完整；它们能捕获异常，但异常信息无法被模型理解；它们能运行，但调用方无法判断任务是成功、失败还是部分完成。这三点构成了 Agent 能否走出 demo、进入生产环境的准绳。
