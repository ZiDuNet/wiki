## 一、核心洞察

Skill不是prompt，是harness。

很多人把Skill当成"写一段更好的prompt"。但真正要让Skill稳定干活，你是在搭一套系统——触发边界、安全规则、references一致性、脚本版本兼容。

这些东西加在一起，早就不是写prompt了。

**Skill的本质是元编程。**

你写的不是业务代码，是"让AI写业务代码的规则"。

就像你教一个实习生，不是给他任务清单，是教他"遇到X情况走Y分支"。

但规则越多，模型的行为越不确定。

这不是模型的问题，是规则本身的复杂度在爆炸。

## 二、三个让人崩溃的问题

### 1. 稳定性陷阱

你加了一个安全检查：「git状态不干净就拒绝执行」。

所有测试都过了。

但用户那边一个全新的、还没

```
git init
```

的skill目录，直接报错退出。

**本质：测试环境永远覆盖不了真实环境的边界。**

### 2. 边界漏洞

你的cleanup函数用字符串排序，iteration-1到iteration-9都好好的。

直到第10轮，iteration-10突然排到了iteration-2前面，cleanup把最新的结果给删了。

**本质：字符串排序 vs 数值排序的经典陷阱。但更深层的是——你测试的轮数永远不够覆盖所有边界。**

### 3. 规则打架

你加了一条安全规则保护A场景。

结果它把B场景的正常路径给封死了，而B场景就写在你自己的协议文档里。

**本质：规则是局部最优，但系统需要全局一致。**

你写的规则在互相打架，而你自己都没发现。

## 三、核心痛点

> "一个「能跑」的skill和一个「真的好」的skill之间，有一条到西天取经那么具体的路。"

这句话太真实了。

"能跑"只是语法通过了、不崩了。

"真的好"是它的行为match你的数据分布，在你定义的输入上，产出你期望的输出。

**类比深度学习：**

训模型不是让代码编过，是让loss收敛。

Skill的"loss"就是它在真实场景下的准确率/满意度。

## 四、8阶段Loop：让Skill自己训练自己

这是文章的核心创新。

作者借鉴了Karpathy的autoresearch（让AI迭代LLM训练代码），做了一个**skill自进化框架**。

### 框架结构（推测）

```
执行 → 捕获失败 → 分析原因 → 生成修复 → 回归测试 → 3层评测 → 5维AND门控 → 选Checkpoint
```

### 3层评测（推测）

1. **单元测试层**：功能是否正确

2. **边界测试层**：极端情况是否崩溃

3. **真实场景层**：在真实用户输入上的表现

### 5维AND门控（推测）

每个维度必须全部通过，才能通过门控：

1. 功能正确性

2. 无回归（不破坏原有功能）

3. 边界覆盖

4. 规则一致性

5. 性能/资源消耗

## 五、我的观点

### ✅ 值得肯定的地方

**1. 从"授人以鱼"到"授人以渔"**

不再一遍遍教skill"不许这样"，而是给它一个目标，让它自己实践、碰壁、改错。

这是真正的机器智能应该有的样子。

**2. 用工程方法解决工程问题**

把skill当成一个需要训练的模型，用loop、评测、门控这套深度学习的方法论来训练它。

思路非常对。

**3. 19轮自进化的实证**

每一轮都揪出了至少一个作者之前完全没看见的问题。

这证明了自进化的价值——**AI能探索人类不想费脑力触达的边界**。

### ⚠️ 潜在问题

**1. 计算成本**

19轮自进化，每一轮都要执行、评测、回归。

这个成本不低。

对于复杂skill，可能需要几百轮才能收敛。

**2. 评测的完备性**

3层评测能覆盖多少真实场景？

如果评测集本身有偏差，skill会过拟合评测集，而不是真正变好。

**3. 规则复杂度的爆炸**

即使有自进化，skill的规则复杂度还是在指数级增长。

门控能挡住bad change，但挡不住"复杂度爆炸"这个根本问题。

## 六、我的想法

### 方向一：分层Skill架构（推荐）

不要把所有规则塞进一个skill。

而是**分层设计**：

```
L1: 核心逻辑Skill（最稳定，最少改动）L2: 边界处理Skill（处理特殊情况）L3: 安全规则Skill（独立模块，可插拔）L4: 路由/调度Skill（决定用哪个Skill）
```

**好处：**

• 核心逻辑稳定，不需要频繁自进化

• 边界处理可以单独进化，不影响核心

• 安全规则独立，可以单独测试和更新

• 路由层负责协调，避免规则打架

### 方向二：形式化验证 + 自进化

在自进化之前，先用**形式化方法**验证关键规则：

```
defverify_skill(skill):# 1. 类型安全assert skill.input_types == skill.expected_input_types# 2. 边界条件for boundary in skill.boundaries:assert skill(boundary)!= crash# 3. 不变量assert skill.invariants_hold(skill.state)# 4. 然后才进入自进化loopreturn skill.self_evolve()
```

**好处：**

用数学证明挡住最明显的bug，自进化只处理"证明不了但实际会出错"的边界情况。

### 方向三：人类在环的渐进式进化

不要一次性跑19轮自进化。

而是**人类在环**：

```
人类评审 → 自进化1轮 → 人类评审 → 自进化1轮 → ...
```

每一轮自进化后，人类快速评审关键变化。

这样：

• 人类可以挡住"过拟合评测集"的change

• 人类可以发现"规则打架"的问题

• 自进化只负责"人类不想费脑力触达的边界"

## 七、总结

这篇文章的核心贡献是：

**用深度学习的方法论来训练Skill，让Skill自己迭代、自己评测、自己回归。**

这个方向是对的，但还有优化空间。

| 维度 | 原文方案 | 更优解 |
| --- | --- | --- |
| 架构 | 单一Skill自进化 | 分层Skill架构 |
| 验证 | 3层评测 | 形式化验证 + 评测 |
| 成本 | 19轮全自动化 | 人类在环的渐进式进化 |
| 复杂度 | 门控挡住bad change | 分层隔离，降低复杂度 |

---

## 八、实战建议

如果你要实践这个框架，我建议：

**1.先用分层架构把skill拆干净**

核心逻辑、边界处理、安全规则、路由调度，四层分离。

**2.对核心逻辑用形式化验证**

最稳定的部分，用数学证明保证正确性。

**3.对边界处理用自进化+人类在环**

自进化负责探索边界，人类负责把关。

**4.对安全规则单独维护，定期审计**

安全规则是系统的底线，不能让它自己进化。

这样既能享受自进化的好处，又能避免复杂度爆炸和过拟合评测集的问题。

---

> 写不进去的那部分，才是你真正的护城河。

Skill自进化的护城河，不是让它自己改代码，而是**人类知道什么时候该停下来**。
