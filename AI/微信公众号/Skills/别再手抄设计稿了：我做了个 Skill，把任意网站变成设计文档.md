# 别再手抄设计稿了：我做了个 Skill，把任意网站变成设计文档

最近我一直在想一个问题：

**为什么 Agent 写代码越来越快，但写出来的页面还是经常不好看？**

不是功能不对。

功能通常没问题。

你让它写一个 landing page、一个 pricing page、一个 dashboard，它能很快把结构、组件、交互都搭出来。

但打开页面之后，经常会有一种很熟悉的感觉：

- 间距看起来不成体系。
- 字号层级像是临时凑的。
- 按钮、卡片、导航各有各的风格。
- 页面能跑，但没有成熟产品那种稳定的设计语言。
- 一眼看上去就是“AI 写的页面”。

这不是 Agent 不会写前端。

而是它缺少一份足够清楚的视觉参考。

人类设计师做页面时，脑子里有大量隐含判断：颜色怎么用、标题多大、卡片圆角多少、按钮怎么压住视觉重心、页面哪里需要留白。

但 Agent 没有这些上下文。

你只说“帮我做一个像 Linear 一样干净的页面”，它只能凭训练记忆去猜。

猜得准的时候，页面还可以。

猜不准的时候，就是一股通用 AI 味。

所以我做了一个 Skill：**website-to-design-md**。

它做的事情很简单：

> 输入一个网址，把这个网站的设计风格逆向工程成一份 AI 能读懂的设计文档。

不是截图，不是临摹，不是让模型凭感觉描述。

而是系统性分析一个网站的视觉规则，然后生成结构化 Markdown，让后续 Agent 写页面时可以直接引用。

项目地址：

github.com/Scofieldfree/website-to-design

## 灵感来自 design.md

最近有个开源项目挺火，叫 **design.md**。

它的思路非常直接：把 Vercel、Linear、Stripe、Notion 这类知名网站的设计风格，写成结构化 Markdown。

这些文档会记录：

- 色彩体系
- 字体层级
- 组件风格
- 圆角和阴影
- 页面间距
- 常见布局模式

Agent 读完这些文档，再去写页面，就不再是凭空发挥，而是有了一份“视觉参考答案”。

这个方向很对。

因为在 Vibe Coding 里，真正拖慢人的往往不是功能实现，而是最后那层视觉质量。

Agent 可以很快写完一个页面。

但如果它没有设计约束，写出来的东西就会飘。

design.md 解决了一部分问题：它给 Agent 提供了成熟网站的设计语言。

但它也有一个明显限制：

**它是一个手工策展的静态语料库。**

也就是说，库里有什么，你才能用什么。

你想参考 Vercel，可以。

你想参考库里没有的 Airbnb、Ramp、Arc、某个小众 SaaS、某个你很喜欢的独立产品官网，就不一定有。

这就产生了一个很自然的问题：

> 与其等别人把设计文档写好，能不能输入任意网址，自动生成一份？

这就是 website-to-design-md 的起点。

## 我做的不是截图分析，而是设计系统逆向工程

很多“网站转设计分析”的做法，其实只是截一张图，然后让模型看图总结：

> 这个网站风格简洁，主色是蓝色，按钮圆角，布局现代。

这种总结看起来有用，但真的拿去指导开发，价值很有限。

因为它太泛。

一个 Agent 真正需要的不是“简洁现代”这种形容词，而是更具体的实现线索：

- 主标题字号是多少？
- 正文行高大概是多少？
- 卡片圆角是 12px、16px，还是 24px？
- 主按钮和次按钮有什么差异？
- 首页 hero 是特例，还是全站通用规则？
- 列表页和详情页的布局节奏是否不同？
- 哪些结论是确定的，哪些只是从截图推断的？

所以 website-to-design-md 的定位不是“看图说话”。

它更像一台设计风格扫描仪。

如果环境里有 Chrome DevTools MCP 或类似浏览器检查工具，Skill 会优先读取真实的 DOM、计算样式、CSS 变量和页面结构。

它会尽量区分：

- 什么是全站稳定规则。
- 什么是某个页面模板特有的规则。
- 什么是某一页的局部处理。
- 什么地方证据不足，需要保守判断。

最后输出的不是一句“这个网站挺高级”，而是一套下游 Agent 能直接消费的设计文档。

## 它和 design.md 的区别

design.md 和 website-to-design-md 解决的是同一类问题：

**让 AI 写页面时有设计参考。**

但两者的路径不一样。

design.md 更像一本“知名网站设计风格字典”。

它提前把一些代表性网站整理好，你需要时直接引用。

website-to-design-md 更像一台“设计风格扫描仪”。

你给它一个网址，它现场分析，现场生成文档。

两者的差异可以这样理解：

**design.md：**

- 静态语料库。
- 覆盖预设网站。
- 通常是一份设计文档。
- 适合快速引用成熟案例。

**website-to-design-md：**

- 动态分析工具。
- 覆盖任意网站。
- 输出分层文档。
- 会记录证据和置信度。
- 更适合你有明确参考对象时使用。

这两个方向并不冲突。

你甚至可以用 website-to-design-md 生成某个网站的设计文档，再把高质量结果贡献回 design.md 语料库。

一个负责积累。

一个负责扩展。

## 两种模式：快速参考和高保真复刻

这个 Skill 现在有两种工作模式。

### 默认模式：快速生成 DESIGN.md

如果你只是输入一个网址，比如：

```
用 website-to-design-md 分析 https://example.com
```

Skill 会生成一份 

```
DESIGN.md
```

。

这份文档适合快速了解一个网站的整体视觉风格。

它会总结：

- 色彩体系
- 字体层级
- 布局节奏
- 组件风格
- 按钮和卡片规则
- 常见视觉模式

这种模式适合“我想参考一下这个网站的气质，但不需要完全复刻”的场景。

比如你想做一个新产品官网，只是希望借鉴某个网站的清爽感、信息密度和组件风格。

### 复刻模式：生成四份文档

如果你明确说：

```
用 website-to-design-md 复刻这个网站的视觉风格
```

Skill 会自动进入更完整的复刻模式。

这时它不只输出 

```
DESIGN.md
```

，还会额外生成三份文档：

**```
TEMPLATE_MAP.md
```**

记录不同页面模板之间的差异。

比如首页、列表页、详情页、定价页分别是什么结构，哪些规则全站通用，哪些只是某个模板特有。

**```
PAGE_BLUEPRINT.md
```**

记录页面的编排节奏。

比如 hero 区域占多高、section 怎么堆叠、卡片一行几个、页面在哪里留白、用户阅读路径怎么走。

**```
EVIDENCE_REPORT.md
```**

记录证据来源和置信度。

哪些结论是 DevTools 直接读到的，哪些是截图推断的，哪些还不确定。

这个分层很重要。

因为真正做页面复刻时，Agent 最容易犯的错就是把局部规则当成全局规则。

比如一个网站首页有一个很夸张的大 hero。

如果所有信息都混在一个文件里，Agent 可能会误以为“全站页面都应该有这样的大 hero”。

分层之后，Agent 能知道：

> 这是首页模板的节奏，不是全站通用规则。

这会明显减少后续实现里的风格漂移。

## 工作流大概怎么跑

Skill 内部会按一套固定流程执行。

### 1. 先检查浏览器能力

如果有 Chrome DevTools MCP、Playwright 或类似工具，就优先用工具读取真实页面数据。

能读计算样式，就不靠截图猜。

能读 CSS 变量，就不凭颜色感觉猜。

这是质量差异最大的地方。

### 2. 自动发现页面

如果你只给了首页 URL，Skill 会尝试从导航和链接里发现同域名的代表性页面。

比如：

- 首页
- 列表页
- 详情页
- 定价页
- 文档页
- 登录页

因为一个网站的设计系统不是只存在于首页。

很多真正稳定的规则，要跨多个页面看才看得出来。

### 3. 构建模板矩阵

发现页面之后，Skill 会按页面角色分类。

它不会把所有页面混成一团，而是先判断：

> 这是哪一种页面模板？

这样后面才能区分全局规则和模板特有规则。

### 4. 采集关键元素证据

对每个页面模板，Skill 会采样关键元素：

- body
- nav
- heading
- paragraph
- button
- card
- input
- badge
- image block
- footer

能检查 hover、focus、sticky 等状态时，也会尽量记录。

### 5. 给结论标注作用域

最后，每条结论都会尽量被标注成不同作用域：

- ```
  global
  ```

  ：全站规则。
- ```
  template-specific
  ```

  ：某类模板特有。
- ```
  page-specific
  ```

  ：某一页的局部处理。
- ```
  uncertain
  ```

  ：证据不足，需要谨慎。

这个标注对下游实现非常关键。

它告诉 Agent：哪些可以大胆复用，哪些不能乱泛化。

## 为什么一定要分层

早期版本我也试过单文件输出。

所有东西都放进一份 

```
DESIGN.md
```

：

- 全局颜色
- 字体规则
- 页面布局
- 模板差异
- 证据说明
- 不确定项

看起来简单，但实际效果不好。

问题是：下游 Agent 很容易混淆信息层级。

它会把“首页独有的 hero 节奏”理解成“所有页面都应该这么做”。

它会把“某个定价卡片的局部样式”理解成“全站卡片统一规则”。

它也不知道某条结论到底是工具确认的，还是模型从截图里猜的。

所以后来我把输出拆成四层。

**```
DESIGN.md
```** 只放稳定、重复出现的全局设计规则。

这份文件可以当项目级设计基线。

**```
TEMPLATE_MAP.md
```** 专门记录不同页面模板之间的差异。

它提醒 Agent：差异是有意设计，不要强行统一。

**```
PAGE_BLUEPRINT.md
```** 记录页面编排和内容节奏。

它解决的不是“组件长什么样”，而是“页面怎么组织”。

**```
EVIDENCE_REPORT.md
```** 记录证据和置信度。

它让 Agent 知道哪里可以确定实现，哪里应该保守处理。

这套分层之后，生成出来的设计文档才更像一个真正可用的设计输入，而不是一篇观后感。

## 一个例子：把 Airbnb 风格迁移到宠物服务网站

仓库里我放了一个 Airbnb 的实战案例。

用 Skill 分析 

```
zh.airbnb.com
```

 之后，会生成四份文档。

```
DESIGN.md
```

 捕获 Airbnb 的全局视觉语言：

- 明亮的白色画布。
- 温暖的近黑文字。
- 珊瑚色 

  ```
  #FF385C
  ```

   作为行动色。
- 系统性的圆角阶梯。
- 图片优先的卡片浏览。
- 搜索胶囊和信任模块。

```
TEMPLATE_MAP.md
```

 记录不同页面模板之间的差异。

比如首页和体验页更偏横向发现轨道，搜索结果页是列表加地图的双栏结构，房源详情页则变成更纵深的信任模块和预订卡片。

```
PAGE_BLUEPRINT.md
```

 记录页面编排节奏。

它会告诉 Agent，页面不是随便堆 section，而是有起承转合。

```
EVIDENCE_REPORT.md
```

 则说明哪些结论来自 DevTools，哪些来自截图推断，哪些地方还不确定。

更有意思的是下游示例。

我用这套 Airbnb 分析文档，生成了一个完全不同领域的**宠物服务预订网站**。

它不是复制 Airbnb 的业务内容。

它迁移的是视觉语言：

- 白色画布。
- 搜索胶囊。
- 图片先行的卡片浏览。
- 克制的行动色。
- 信任模块。
- 柔和但稳定的圆角体系。

这说明提取出来的东西不是“Airbnb 的具体页面”，而是它背后的设计系统。

这才是我真正想要的结果：

> 让 Agent 学到一个网站的设计语言，而不是抄一张截图。

## 怎么使用

安装方式很直接。

把仓库里的 

```
skills/website-to-design-md
```

 目录加载到你的 Agent Skill 系统里。

无论你用的是 Cursor、Claude Code、Copilot，还是其他支持 Skill 的 Agent 环境，本质上都是让 Agent 读到这套 Skill 指令。

最简单的调用方式：

```
用 website-to-design-md 分析 https://example.com
```

如果你要更高保真地复刻风格，就说清楚：

```
用 website-to-design-md 复刻 https://example.com 的视觉风格
```

想要更好的结果，可以额外补充：

- 你最关心哪些页面。
- 目标技术栈是什么。
- 是做参考，还是做高保真复刻。
- 是否需要输出给某个项目使用。

比如：

```
用 website-to-design-md 复刻这个网站的视觉风格。 URL: https://example.com 重点分析：首页、定价页、博客详情页。 目标栈：Next.js + Tailwind + shadcn/ui。 输出要能指导 Agent 实现一个新的 SaaS 官网。
```

越明确，输出越稳定。

## 什么时候适合用

这个 Skill 不是为了替代设计师。

它更适合这几种场景：

**你在做 Vibe Coding，但页面总是不够好看。**

这时候与其继续让 Agent 自己发挥，不如给它一份成熟网站的设计文档。

**你想借鉴某个网站的视觉语言。**

不是抄内容，而是学习它的颜色、排版、组件、留白和页面节奏。

**你要做一个新产品，但缺少设计系统起点。**

先找几个同类优秀网站跑一遍，提取共性，比从空白开始更稳。

**你希望 Agent 输出更一致。**

当 Agent 有了设计基线，后续页面就不容易每次长得不一样。

不适合的场景也很明确：

如果你只是做一个一次性 demo，或者完全不在乎视觉一致性，直接让 Agent 写就行。

这套流程的价值在于：当你开始关心“页面是否像一个成熟产品”，它能显著降低返工。

## 我为什么觉得这件事重要

很多人讨论 AI 编程时，重点都放在“它能不能写代码”。

但在真实产品开发里，代码只是其中一层。

尤其是前端。

用户看到的不是你的组件结构，也不是你的状态管理。

用户看到的是页面。

如果页面视觉不稳定，哪怕功能全对，产品也会显得不成熟。

这就是当前很多 Agent 前端输出的问题：

**实现能力已经很强，但设计输入太弱。**

所以我更倾向于把问题拆开：

Agent 负责快速实现。

设计文档负责提供视觉约束。

浏览器工具负责提供真实证据。

Skill 负责把这些东西串成稳定流程。

这样 Agent 就不再是在黑盒里“凭感觉设计”，而是在一套可追溯的设计输入上工作。

这比单纯写更长的 prompt 要可靠得多。

## 结尾

我做 website-to-design-md，不是为了让 AI 去抄网站。

而是为了让 AI 真正读懂网站的设计语言。

从一个网址里提取出：

- 全局颜色和字体。
- 组件规则。
- 页面模板差异。
- 内容编排节奏。
- 证据和不确定性。

然后把这些变成 Agent 能消费的文档。

这样下次你再让 Agent 写页面时，它不再只有一句模糊的“做得像某某网站”，而是有一份可执行的视觉规格。

这就是我想解决的问题：

> 不要再让 Agent 凭空猜设计。

> 给它一份真正能读懂的设计文档。

项目地址：

github.com/Scofieldfree/website-to-design

装上 Skill，对你喜欢的网站跑一遍。

你会很直观地看到：有设计参考答案和没有设计参考答案，Agent 写出来的页面不是一个级别。
