你不是缺一个更聪明的模型。
你缺的是：让模型“按工程流程干活”的手脚。

mattpocock/skills 这套 Skill 的价值不在于提示词写得多漂亮，而在于它把工程师每天重复的三类工作，做成了可复用、可执行、可验收的流程：

- 需求怎么写清楚（PRD）
- 活怎么拆到能独立交付（Issues / tracer bullet）
- 怎么写到不烂尾（TDD 的竖切循环）

下面用工程视角，把它拆开讲透：你可以怎么用、它为什么好用、以及落地时最容易踩的坑。

很多人用 Agent 的体验是这样的：

- 代码能吐一堆
- PR 也能开
- 但最后你拿到的是一堆“看起来能用”的片段

真正工程交付要解决的是三件事：

1. 目标可对齐：到底要做什么
2. 过程可推进：怎么拆、怎么排依赖
3. 结果可验证：怎么测、怎么证明没回归

mattpocock/skills 的核心，就是把这三件事固化成可重复执行的 Skill。

## 四个最该先用的 Skill（一个闭环） 🔁

这套仓库里 Skill 很多，但最能快速拉开差距的是这四件：grill-me → to-prd → to-issues → tdd。

它们刚好是一条链：

- grill-me：先把方案“问到不含糊”，把决策树每个分叉都走完
- to-prd：把上下文固化成 PRD（可审查）
- to-issues：把 PRD 拆成 tracer bullet 竖切（可并行、可验收）
- tdd：用红绿重构把每个切片做成可验证的交付

### 0) grill-me：在写 PRD 之前，先把方案“问到没漏洞”

很多项目烂尾不是因为实现难，是因为你在开工前把关键问题都跳过了：边界条件是谁定的？失败策略是什么？哪些决策必须先拍板？

grill-me 的做法很简单但很狠：它会沿着设计/方案的决策树一路追问，每个问题一次只问一个，并且会给出它建议的答案；直到你们对方案的每个分叉都达成一致。

这个 Skill 特别适合用在两种场景：

- 你觉得“方案差不多了”，但心里不踏实（怕遗漏）
- 你要把活交给 Agent/新人推进，想先把不确定性压到最小

用一句话概括：grill-me 不是帮你写文档，它是帮你把“还没想清楚的地方”逼出来。

### 1) to-prd：不采访你，直接把上下文“落成 PRD”

它的要求很硬：

- 不要再追问用户（“Do NOT interview the user”）
- 直接用当前对话 + 代码库现状，产出 PRD
- 强制输出：Problem / Solution / 大量 User Stories / Implementation Decisions / Testing Decisions / Out of Scope

这对工程很关键：

- 你不需要再跟模型“聊半天聊不出结论”
- 你得到的是一份可以放进 issue、可以让团队讨论的文档

### 2) to-issues：用 tracer bullet 竖切，把活拆成“可独立抓取”的 issue

这个 Skill 最强的一点：它明确反对“横切拆分”（按层拆：先 DB、再 API、再 UI）。

它要求你拆的是 tracer bullet 的“竖切切片”：

- 每个 slice 都要贯穿所有集成层（schema/API/UI/tests）
- 每个 slice 单独完成后都能 demo/验证
- 宁可多切薄片，也别少切厚块

并且它还有一个特别实用的工程分类：

- HITL：需要人参与决策/评审
- AFK：可以让 Agent 连续干完、你回来验收就行

这相当于把“哪些必须人拍板”显式化了，减少了最浪费时间的往返。

### 3) tdd：把 TDD 从口号变成流程（而且反对一次性写完所有测试）

它把“写测试”讲得很工程：

- 好测试：验证 public interface 的行为（integration 风格），不要绑实现细节
- 坏测试：mock 内部协作者、测私有方法、重构一动就碎

更重要的是，它点名批评一个常见伪 TDD：

- RED：一次性把 test1~testN 全写完
- GREEN：再一次性把 impl1~implN 全补上

这会让你写出“想象中的行为”的测试，最后测试既不敏感也不可靠。

它要的是真·竖切循环：

- 一次只写一个行为的测试
- 只写最少代码让它过
- 一路重复，最后再 refactor

## 你可以直接照抄的落地流程（一个人也能跑起来） 🧪

把它当成一条流水线：

1. 先用 grill-me 把方案问到不含糊：边界、失败策略、必须拍板的决策点
2. 把你们聊出来的共识交给 to-prd，落成 PRD（变成“可审查的文本”）
3. 用 to-issues 把 PRD 拆成 tracer bullet 竖切（变成“可并行的任务”）
4. 针对每个 slice，用 tdd 跑红绿重构（变成“可验证的交付”）

仓库 README 给的安装方式是：

```
npx skills@latest add mattpocock/skills/grill-menpx skills@latest add mattpocock/skills/to-prdnpx skills@latest add mattpocock/skills/to-issuesnpx skills@latest add mattpocock/skills/tdd
```

你不需要一口气装全套。先把这三个跑顺，你的 Agent 使用方式会完全变样。

## 例子：把“做一个功能”变成“可交付的切片” 🧩

假设你要做一个很常见但很容易烂尾的需求：

“给系统加一个导出功能（CSV），支持筛选条件，导出后能追踪下载记录。”

传统拆法（横切）会变成：

- 先加表
- 再写 API
- 再写前端
- 最后补测试

最后你会卡在：接口不对、字段变来变去、测试补不动。

按 to-issues 的竖切思路，你更可能得到这种切片（示意）：

- Slice 1（AFK）：最小导出链路跑通：前端按钮 → API 返回固定 CSV（哪怕只有两列）→ 下载成功（可验收）
- Slice 2（AFK）：把 CSV 生成改为真实数据 + 最小筛选（可验收）
- Slice 3（HITL）：确认筛选语义/字段口径（需要产品/业务拍板）
- Slice 4（AFK）：导出记录落库 + 列表可查询（可验收）
- Slice 5（AFK）：补关键路径的集成测试（可验证）

每一片都能独立合并、独立回滚、独立 demo。

这就是“让 Agent 真正变得可用”的关键：不是一次性写对，而是能持续推进、持续验证。

## 最容易踩的 3 个坑（提前躲开） ⚠️

1. 把 Skill 当成“提示词模板”

Skill 的本质是流程约束。你如果只复制一段 prompt，不按它的输出结构/检查点走，效果会大幅打折。

1. 竖切被你写回“按层拆分”

写 issues 时最常见的退化：

- “加数据库表”
- “写后端接口”
- “写前端页面”

这不是 slice，这是按层排队。真正 slice 的验收标准是：完成后能 end-to-end 验证。

1. 写测试写成“测实现”

tdd 里最重要的一句：测试要验证 public interface 的行为。

如果你的测试每次重构都要大改，那你不是在用测试保护行为，你是在用测试锁死实现。

## 一句话总结（你可以把它当成团队规范） ✅

- PRD：把上下文固化成可审查的文本
- Issues：用 tracer bullet 竖切，让每个任务可独立交付
- TDD：一条行为一个循环，测试只管外部行为，不绑内部实现

这三步跑顺了，Agent 才不是“帮你写代码”，而是“帮你交付工程”。
