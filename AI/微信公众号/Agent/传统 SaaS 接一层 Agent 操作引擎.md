很多企业已经接受了一个现实：下一代 B2B 软件不只是给人点按钮，也要让 Agent 代替人去查客户、建报价、发审批、追工单。问题不在愿不愿意做，而在大多数老 CRM、ERP、本地 OA 根本不是按这个方向长出来的。

这些系统往往已经把业务能力做得很深，但能力被埋在页面按钮、历史字段、审批脚本和内部接口里。人点起来没问题，Agent 一接就会暴露短板。接口命名混乱、返回语义不稳、写操作副作用太大，模型根本不该直接面对这些原始能力。

更现实的改造路径，是在旧系统前面插入一层操作引擎：先拦住 API 流量，提炼稳定动作，再把这些动作注册成 OpenAPI 契约，最后补上审批、补偿和追踪。旧系统继续提供业务能力，Agent 只面对被整理过的操作面。

传统 SaaS 的 Agent 化改造，重点是把“人能点的旧功能”整理成“机器能安全调用的动作层”。

## 一、为什么大多数旧系统不值得整体重写

老 CRM/ERP 的主要问题，在于业务能力的表达方式过于面向人工操作。客户档案、报价审批、订单变更、库存冻结、发票冲销，这些能力早就存在，只是被历史前端和历史接口绑住了。

这时如果直接启动“新一代 Agent 原生 SaaS 重写计划”，风险往往比想象中大得多。旧系统里的字段约定、审批链、异常分支、账务边界和补丁逻辑，很多都没有完整文档，只活在数据库、页面行为和少数核心员工的经验里。一次性迁移，最容易把业务连续性一起迁走。

更稳的方式，是先采用代理式改造。外部入口统一先过一层门面，旧能力继续在后面跑，新能力按动作逐步迁出。这样改造节奏是可控的，客户端也不需要立刻知道后面哪些能力已经换了，哪些还留在老系统里。换成更工程化的说法，就是先给这套庞大的有界面系统，补上一层面向 Agent 的 Headless 操作面。

适合先上 Agent 操作层的 4 个信号

1. 老系统功能足够深，但交互极重，必须依赖熟练员工点很多步。

2. 同一类动作在多个入口重复出现，例如 Web、移动端、企业微信、小程序。

3. 系统已经有 API 或内部服务，只是语义凌乱，不适合直接给模型。

4. 业务不允许长时间停机重构，但允许逐步把高频动作抽出来重做。

## 二、Agent 接不进旧系统，卡的其实是操作语义层

这层问题和“有没有 API”不是一回事。很多旧系统接口很多，但那是面向前端页面或历史中台写的，不是面向 Agent 写的。接口名像 saveForm、execAction、submitFlow，参数里塞满页面状态和内部标志位，模型根本无法凭这些名字判断动作边界。对于人类，这些名字还有页面文案和按钮位置帮忙兜底；对于大模型，这就是一个高熵黑盒。模型无法通过函数名推断出它到底是在存草稿、提交流程，还是已经触发了扣库存。操作代理层的本质，就是先把这些高熵接口做一轮语义降熵。

更麻烦的是副作用。一个看起来像“保存草稿”的接口，可能顺手写了审计日志、推进了状态机、发了通知，甚至锁了库存。人操作时会被页面文案、权限按钮和审批弹窗约束，模型直接调接口时，这些约束全都消失了。

| 旧系统接口 | Agent 需要的动作契约 |
| --- | --- |
| 面向页面状态，参数混着表单字段、按钮来源、内部标志位 | 面向业务动作，参数只保留业务必需信息和明确约束 |
| 响应常常只有 code/msg，业务失败混在成功状态里 | 返回显式的业务状态、下一步可执行动作和副作用说明。这决定了 Agent 会继续推进，还是困在“成功了，但接下来该做什么”这种推理断点里。 |
| 读取、草稿、正式提交揉在一起 | 读取、草稿、审批、提交明确分层 |
| 权限依赖前端按钮和员工角色默认继承 | 权限收口到本次任务、本次工具和本次审批 |

所以真正要补的，是一层面向 Agent 的操作语义。它把老系统那堆能跑但难懂的内部能力，重新整理成 Agent 可理解、可验证、可审计的动作集合。

## 三、第一步先拦 API 流量，从真实操作里抽动作

这时最有价值的输入，是系统里每天真实发生的高频操作。销售怎么建报价，客服怎么发退款草稿，财务怎么冲销发票，仓库怎么锁库存，这些动作早就以页面请求、网关日志、下游调用链的形式存在。

把流量先拦住，意义不在于录一堆包，而在于提炼稳定动作。哪条路径是真正的读取，哪条路径只生成草稿，哪条路径会触发不可逆副作用，哪条路径必须等待人工确认，这些都应该先从流量和现网行为里抽出来，再决定怎么暴露给 Agent。

代理层在这里很关键。它既能保持外部入口不变，也能把外部看起来干净的动作 URL 重写成老系统真正能够接受的内部格式。旧后端不用立刻改，操作层先把语义和路由整理干净。

从流量里抽动作时，先做这 4 件事

1. 只抓高频、高价值、边界相对稳定的动作，不要一开始就覆盖整套 ERP。

2. 把读取、草稿、正式提交拆开，尤其把高副作用写操作单独拿出来。

3. 把原始错误码翻译成业务状态，例如可重试、业务拒绝、权限不足、需要人工升级。

4. 为每个动作补充调用前置条件、幂等键和审计标识，别让 Agent 直接继承原始接口的松散语义。

动作被提炼出来之后，下一步是把这些动作变成一份显式契约，让 Agent 框架、Copilot 平台和企业内部网关都能理解同一套能力定义。

从流量日志里识别出“创建报价草稿”这类稳定动作之后，团队会马上遇到一个工程选择：是把它继续写死在中间代码里，还是用一种机器和人都能读懂的契约语言把它描述出来。对于当前的 Agent 生态，OpenAPI Specification 仍然是连通大模型工具调用与业务系统的最低阻力路径。它不仅是文档，更是告诉模型“哪些参数是必填、哪些状态代表业务失败、接下来还能做什么”的事实来源。

## 四、OpenAPI 在这里充当动作注册表

很多团队把 OpenAPI 只当成对外文档，但在 Agent 场景里，它承担的是动作注册表的角色。操作名、参数含义、响应结构、错误说明、示例输入，这些都直接影响模型能否选对工具、传对参数、在失败后自我修正。

这里有一个重要判断：不要把老系统原始接口原封不动塞进 OpenAPI。给 Agent 的契约应该比给前端页面的契约更窄、更清楚。端点名要直指业务动作，描述里要写清适用条件和边界，参数类型尽量具体，响应里要明确下一步允许做什么。

```
openapi: 3.0.1 paths:   /quotes/draft:     post:       operationId: create_quote_draft       summary: 创建报价草稿，不触发正式审批       description: 仅在客户状态为有效且商品价格已校验时调用       requestBody:         required: true       responses:         "200":           description: 返回草稿编号与下一步可执行动作         "409":           description: 客户状态或价格规则不满足，不能建草稿
```

一旦动作层有了这类契约，它就可以被多种 Agent 运行时重复利用。无论是接入企业内部自研编排层，还是挂到 Agent SDK、Copilot 平台或 Bedrock 的 Action Group，大家看到的都会是同一层被整理过的业务动作，而不是老系统背后那堆历史接口。

如果团队当前的 Agent 运行环境支持 MCP，也就是 Model Context Protocol，这层操作代理还可以进一步封装成一个 MCP Server。这样做的意义，不是替代 OpenAPI，而是把已经整理好的动作层，用更贴近 Agent 工具生态的方式继续暴露出去。OpenAPI 负责定义契约，MCP 负责把契约接进支持该协议的助手、IDE 或桌面 Agent。

## 五、上线前还要补齐审批、补偿、追踪和最小权限

到这里，旧系统已经有了可供 Agent 调用的动作面，但距离生产可用还差最后一层治理。真正决定它能不能长期跑起来的，是危险动作有没有人能拦，失败之后能不能收，出问题能不能追，权限是不是只开到最小。

生产可用的 4 层控制面

**1. 审批与人工中断：** 高风险动作在真正提交前暂停，等待人工批准、拒绝或修改参数。价格改写、退款执行、合同发送这类动作都不该自动直通。

**2. 补偿与幂等：** 一条动作链失败后，系统必须知道哪些步骤可以重试，哪些需要补偿，哪些已经进入不可逆阶段。退款、库存、发票都不能靠“失败就再调一次”处理。

**3. 全链路追踪：** 每次 Agent 调用都要带上统一追踪标识，能回看到底命中了哪个动作、重写到了哪个旧接口、在哪个环节被审批或拒绝。

**4. 最小权限暴露：** 不要把整套旧系统一次性暴露给模型。先开放少量高频工具，再用允许名单、动作白名单和审批策略逐步放权。

这四层一旦补齐，Agent 就会成为受业务边界约束的执行层。它能加快软件使用过程，但不会绕开企业必须保留的管理边界。这里说的“操作引擎”也不一定是一套重型中间件，很多团队的第一版完全可以只是 

```
API 网关策略 + 一组 OpenAPI YAML + 一个轻量级的 MCP Server 或代理服务
```

。

## 六、综合图：旧 SaaS 接入 Agent 操作引擎的完整路径

把前面的层次重新拼起来，传统 SaaS 的 Agent 化改造会呈现为一条经过门面代理、动作契约、审批补偿和追踪收口的执行链。优先需要补上的，是系统与自动化之间那层可安全调用的操作面。

点击图片可放大查看高清架构。

旧 SaaS 接入 Agent 操作引擎综合图Agent 与业务入口企业微信 / Web 助手 / Copilot / 内部编排层操作代理层流量拦截 / URL 重写 / 参数翻译 / 响应标准化把旧接口整理成稳定动作动作注册表OpenAPI Spec / 操作描述 / 参数类型 / 示例与错误语义Agent 只看到这一层，不直接看到旧系统内部协议控制与治理层审批中断 / 幂等键 / 补偿动作动作白名单 / 风险分级 / 人工接管决定哪些动作能自动放行观测与审计层trace\_id / 调用日志 / 失败原因原始动作与补偿动作双向关联保证能回放、能追责、能定位旧 CRM / ERP / OA / 财务系统继续保留，只把稳定业务能力通过动作层重新暴露

这张图里最关键的一点，是 Agent 永远不直接碰老系统的原始协议。它只面对一层被缩窄过的动作面。后面接的是老 ERP，还是未来新服务，对 Agent 来说都只是实现细节。

图里左右两个模块最好分开看。左边的控制与治理层，决定的是“能不能动”；右边的观测与审计层，记录的是“动了什么”。少了左边，Agent 会变成越权执行器；少了右边，系统出了问题只能靠猜。

这也是为什么传统 SaaS 的竞争边界正在变化。过去比的是谁的页面更全、谁的流程更细；接下来更重要的问题会变成，谁能更快把旧能力抽成机器可调用的动作层，并且让这层能力能安全地挂给 Agent。

给技术负责人的 3 个立即可做动作

1. 找出过去 30 天调用量最高的 3 个写操作接口，例如创建订单、更新客户、提交审批。

2. 在 API 网关或代理层单独落一份这些接口的请求 JSON，先观察真实入参里哪些是前端状态，哪些才是业务字段。

3. 选其中一个最稳定的动作，删掉明显的页面噪音字段，写出一版 10 行左右的 OpenAPI 描述，先让动作层从文档上独立出来。

总结快照

1. 旧 CRM/ERP 的改造重点，是先把外部入口和动作语义稳定下来。

2. API 流量拦截的目标，是从真实操作里抽出稳定业务动作。

3. OpenAPI 在 Agent 场景里更像动作注册表，不该照搬老接口原始形态。

4. 审批、补偿、追踪和最小权限补齐之后，Agent 才能成为 B2B 软件的隐形驾驶员。

传统 SaaS 是一个巨大的“知识库”，价值斐然，也极具先发优势！用户每天要跟SaaS系统交互，而与此同时，基于大模型的 Agent的优势也是交互，所以SaaS + Agent的方向，你找到了吗？
