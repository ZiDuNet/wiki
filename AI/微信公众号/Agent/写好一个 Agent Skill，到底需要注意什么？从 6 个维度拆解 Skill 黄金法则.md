为什么你的 Skill 写了等于没写？
AI 还是乱猜、还是踩坑、还是每次都要你重新教？
问题不在 AI，在你的 Skill 写法。

---

## 开篇：大多数 Skill 的死法

我见过很多 Skill，写法基本是这个套路：

`---
name: code-review
description: 代码审查
---
请帮我审查代码，找出bug，给出修改建议。
`

看起来没毛病，对吧？

但你用起来就会发现：

· AI 经常想不起来用这个 Skill——因为 description 太模糊

· 用了之后输出也不稳定——因为指令就一句话，AI 全靠猜

· 每次还要你手动补充"重点看安全漏洞""用中文回复""输出要用表格"——因为该写的东西都没写

**写 Skill 不是写 Prompt。Prompt 是一次性的，Skill 是跨会话复用的操作手册。**

一次 Prompt 没写好，这次对话忍一忍就过去了。但 Skill 没写好，每次对话你都要重新教 AI 一遍——这比不用 Skill 还痛苦。

接下来，我从 6 个维度拆解：写好一个 Skill，到底需要注意什么。

每条法则，都会给你"反面写法"和"正面写法"的对比。读完就能直接上手改你自己的 Skill。

---

## 法则一：Description —— 触发率决定生死

Description 是 Skill 的门面。它决定了 AI 会不会在正确的时机"想起来"用这个 Skill。

但大多数人的写法，AI 根本记不住。

反面写法

`description: 处理PDF文档
`

三个字：太模糊。AI 不知道什么场景该用它——用户说"帮我看看这个文件"的时候不会触发，说"这个PDF打不开"的时候也不会触发，因为它不知道这个 Skill 到底是解析 PDF、合并 PDF 还是给 PDF 加水印。

正面写法

`description:
从PDF文档中提取文本和表格数据，支持扫描件OCR识别。
当用户上传PDF文件要求提取内容、解析表格、或提到
"这个PDF读不出来""扫描件识别"时使用此技能。
`

写好 Description 的公式

`做什么 + 什么时候用 + 典型触发词
`

· **做什么**：一句话说清这个 Skill 的核心能力

· **什么时候用**：明确触发场景，帮助 AI 做匹配判断

· **典型触发词**：列出用户可能会说的原话，大幅提升触发率

别小看"典型触发词"这步。加上之后，Skill 的激活率至少翻一倍。

## 法则二：结构 —— 像函数一样设计边界

Skill 不是越大越好，也不是越小越好。**一个 Skill 应该完成一个"连贯的工作单元"。**

怎么判断边界对不对？

问自己一个问题：**能不能用一句话说清这个 Skill 解决什么问题？**

· 能说清 → 边界合理

· 要用"同时还要"来凑 → 太大了，该拆

· 说完发现太碎，还得配合另一个 Skill 才能用 → 太小了，该合

反面设计：一个 Skill 管全流程

`name: project-delivery
description: 项目交付全流程管理
`

这个 Skill 试图管理需求分析、方案设计、开发实施、测试验收、上线部署——看起来很"全"，但实际上：

· 指令太多太长，AI 不知该先执行哪部分

· 不同阶段需要的知识完全不同，全塞一起反而互相干扰

· 某个环节出了问题，改起来牵一发动全身

正面设计：按阶段拆分

`requirement-analysis/ → 需求分析，输出需求确认单
solution-design/ → 方案设计，输出技术方案文档
delivery-acceptance/ → 交付验收，输出验收报告
`

每个 Skill 独立可用、独立可测、独立可迭代。

拆分 vs 合并的决策框架

| 场景 | 建议 |
| --- | --- |
| 步骤之间有明确的先后依赖 | 独立为多个 Skill，用流程串联 |
| 用户通常一次就触发其中一个 | 拆开，不要打包 |
| 用户每次都要同时用两个 Skill | 合并为一个 |
| 合并后指令超过 200 行 | 拆分，200 行是经验上限 |

## 法则三：指令 —— 写"方法"而非"答案"

这是写 Skill 最容易犯的错：告诉 AI "输出什么"，而不是教它"怎么思考"。

反面写法：直接给答案模板

`## 输出格式
请按以下格式输出代码审查结果：
| 文件 | 行号 | 问题 | 严重程度 | 建议 |
|------|------|------|----------|------|
| ... | ... | ... | ... | ... |
`

AI 确实会按这个格式输出。但它不知道：

· 安全漏洞和代码风格问题哪个更重要

· 哪些类型的 bug 应该重点排查

· 发现问题后应该给修复代码还是只给描述

结果是格式对了，内容空洞。

正面写法：教思考框架

`## 审查步骤
### 1. 先扫安全
优先检查：SQL注入、XSS、硬编码密钥、未校验的输入。
安全问题标为"高"，必须给出修复代码。
### 2. 再看逻辑
重点关注：空指针、数组越界、资源未释放、并发问题。
逻辑缺陷标为"中"，给出修复建议。
### 3. 最后看风格
命名规范、重复代码、可读性。
风格问题标为"低"，仅列出不改也能跑。
### 输出
按严重程度从高到低排列。高严重度问题必须附修复代码。
`

区别在哪？

· 反面写法给的是**格式**——AI 只知道"长什么样"

· 正面写法给的是**方法**——AI 知道"怎么想"以及"什么重要"

一个教方法的 Skill，换个项目、换个语言，照样好用。一个只给格式的 Skill，换个场景就废了。

预设默认值，减少 AI 犹豫

还有一个实用技巧：**直接告诉 AI 推荐方案，不要让它选。**

`## 依赖安装
默认用 uv run 执行 Python 脚本（自动装依赖）。
如果没有 uv，再用 pip install -r requirements.txt。
不要问用户"你想用哪个包管理器"。
`

AI 最大的问题不是能力不够，而是在不该犹豫的地方犹豫。预设默认值，给它一条明确的执行路径。

## 法则四：坑点 —— 最有价值的部分，大多数人跳过了

如果说前面三条法则是"让 Skill 能用"，那这条法则就是"让 Skill 好用"。

**坑点（Gotchas）是 Skill 里最有价值的部分，但也是大多数人跳过的部分。**

为什么不写？因为坑点只能从踩坑中提炼。你没踩过，就写不出来。但一旦你踩过并记录下来，这个 Skill 就从"能用"升级为"好用"。

三个真实的坑点案例

**案例一：投标分析——扫描件陷阱**

`## ⚠️ 坑点
- 60% 的政府招标 PDF 是扫描件，pdfplumber 直接提取为空。
必须先判断：提取结果是否为空？为空则自动切换 OCR 流程。
不要等到用户反馈"怎么没有内容"才发现。
- 星号项（★）的★号有些是图片不是文字，OCR 时可能丢失。
建议同时用正则匹配"星号项|★项|实质性要求"等关键词兜底。
- "不支持"三个字不能出现在差异分析报告里。
政府客户看到直接判负。所有不满足项统一写为
"替代方案：XXX，详见附件X"。
`

这三个坑，是投标团队在三次废标后总结出来的。不写进 Skill，AI 每次都会重新踩。

**案例二：公众号文章发布——列表渲染灾难**

`## ⚠️ 坑点
- 微信公众号会过滤

1. 标签，列表渲染极不稳定。
   所有列表必须用

   标签 + "·" 前缀替代。
   不是"建议"这么做，是"必须"这么做。
   - 微信给表格自动加灰色边框，无法通过 CSS 去掉。
   所有 table、tr、td 必须显式加 border: none。
   - 封面图尺寸严格 900×383，不是这个比例会被裁切。
   不要用其他尺寸"差不多就行"。
`

这些坑，是在连续发布失败五次、每次都要手动改 HTML 后总结出来的。

**案例三：数据清洗——编码地狱**

`## ⚠️ 坑点
- Excel 导出的 CSV 默认用 GBK 编码，不是 UTF-8。
pd.read_csv() 不指定 encoding 会直接报错。
推荐先用 chardet 检测编码，再读取。
- 日期格式百花齐放：2024-01-01、2024/1/1、20240101、
"2024年1月1日" 可能出现在同一列。
清洗前先 pd.to_datetime(infer_datetime_format=True)。
- 数值列里混入"未统计""N/A""-"等文字很常见。
不要直接 astype(float)，先用 replace 统一替换为 np.nan。
`

写坑点的模板

每个坑点按这个结构写：

`触发条件 → 翻车后果 → 推荐做法
`

不需要文学性，需要的是精准。AI 看到触发条件就知道"哦这个场景要小心"，看到推荐做法就知道"遇到这种情况这样处理"。

## 法则五：渐进式披露 —— 别一口气把所有东西塞给 AI

Skill 有一个很精妙的设计机制：**渐进式披露**。

它不是一个文件从头读到尾，而是分三个阶段按需加载：

| 阶段 | 加载什么 | 类比 |
| --- | --- | --- |
| 发现 | name + description | 你看到菜单上的菜名和简介 |
| 激活 | 完整 SKILL.md | 你点了这道菜，看到完整做法 |
| 执行 | scripts/ + references/ | 厨师开始备料、查配方 |

为什么这很重要？

因为 AI 的上下文窗口是有限的。你的 Skill 文件越大，塞进上下文的信息越多，留给实际推理的空间就越少。

想象一下你的桌面上同时摊开了 20 份操作手册——你还能专心干活吗？AI 也一样。

实践建议

**SKILL.md 控制在 150 行以内。**

· 核心指令 + 坑点 + 输出模板，150 行足够

· 如果超过 200 行，说明这个 Skill 太胖了，参考法则二拆分

· 详细的 API 文档、配置说明、参考资料 → 放到

```
references/
```

 目录，按需加载

· 可执行脚本 → 放到

```
scripts/
```

 目录，AI 需要时才调用

`my-skill/
├── SKILL.md ← 150行以内，精炼的操作手册
├── references/ ← 详细文档，按需加载
│ ├── api-spec.md
│ └── config-guide.md
└── scripts/ ← 可执行脚本，按需调用
└── helper.py
`

**把 SKILL.md 当成一份快速参考卡（Cheat Sheet），不是一本教科书。**

## 法则六：评估 —— 别凭感觉，用数据说话

Skill 写完了，怎么知道它真的有效？

大多数人的做法是"用几次感觉还行就过了"。但感觉是不靠谱的——你今天觉得好用，明天换个场景可能就翻车了。

核心方法：A/B 对比

**同一个任务，带 Skill 跑一次，不带 Skill 跑一次，对比结果。**

就这么简单。

一个最小可行评估方案

你不需要复杂的评测框架，3 个断言就能起步：

`{
"skill_name": "bid-analysis",
"evals": [
{
"id": 1,
"prompt": "帮我分析这份招标文件的技术参数差异",
"files": ["evals/sample-bid.pdf"],
"assertions": [
"输出包含三线表格式的差异分析",
"所有星号项均已识别并标记",
"没有出现'不支持'字样"
]
}
]
}
`

三个断言，对应三个核心质量要求。通过了就说明 Skill 在关键维度上有效。

四个信号灯

跑完对比测试后，看信号灯判断下一步：

| 信号 | 含义 | 行动 |
| --- | --- | --- |
| 带 Skill 通过，不带也通过 | 断言太弱，没有区分力 | 加更有挑战的测试用例 |
| 两种都失败 | 断言或用例本身有问题 | 先修测试，再评估 Skill |
| 带 Skill 通过，不带失败 | Skill 明确有价值 | 继续强化 |
| 有时通过有时失败 | 指令存在歧义 | 收紧指令，加具体示例 |

判断标准

通过率提升 50% 以上，额外开销不到 15 秒 → **值得用。**

Token 翻倍但通过率只提升 2% → **不值得，该精简。**

## 收尾：Skill 是活的，不是写完就结束

写好一个 Skill，不是终点。

前沿的研究已经在探索 Skill 的自进化——让 Skill 在使用过程中自动发现问题、自动迭代改进。比如：

· **从执行轨迹中蒸馏 Skill**：记录每次成功和失败的操作路径，自动提炼出可复用的经验

· **生成-验证对抗闭环**：一个模块负责改 Skill，另一个模块负责出题验证，互相博弈着进化

· **群体进化**：多个用户的经验汇聚到共享 Skill 库，白天收集证据，夜间自动优化

这些方向的共同指向是：**Skill 正在从"静态的操作手册"进化为"动态的能力资产"。**

但不管技术怎么演进，今天讲的六条法则不会过时——因为它们解决的是"如何把你的经验准确地传递给 AI"这个根本问题。

**从哪里开始？**

从你最重复、最烦人的那个任务开始。

把它和 AI 协作的过程记录下来——你在哪里纠正了它？哪些错误反复出现？把这些"修正记录"提炼成 Skill 的步骤和坑点。

你会发现：**写 Skill 的过程，本质上是在梳理你自己的业务方法论。**

最好的 Skill，不是 AI 帮你写的，是你踩过的坑帮你写的。
