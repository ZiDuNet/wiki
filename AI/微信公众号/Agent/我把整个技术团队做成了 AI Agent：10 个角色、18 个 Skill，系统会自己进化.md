# 一、从一个 CTO 的真实崩溃说起

我同时担任三个职位：CTO、架构师、部门总监。

管着研发、测试、需求、UI、PMO 五个团队，二三十号人。

每天的状态是这样的：

上午刚跟客户聊完技术方案，下午要评审三个 MR，晚上还得写月度运营会的议题。

重复的工作把我的时间切成了碎片。

**技术选型**——同样的对比维度，每次都要重新想一遍。
**架构评审**——同样的检查清单，每次都靠脑子记。
**项目周报**——同样的格式，每次都让人帮我汇总，汇总完还要改。
**会议纪要**——开完会说要整理，三天后还在草稿箱。

最让我崩溃的不是工作量，而是：**这些事情没有一件是真正需要我来做的。**

它们需要的是「标准」，不是「我」。

于是我花了两周时间，做了一件事：

**把整个团队的每一个角色，都做成了 AI Agent。**

包括我自己。

---

## 二、这套系统长什么样

先看全貌，再讲细节。

整个体系分四层：

```
ai-team/
├── shared/          # 🌐 全局层 — 影响所有 Agent 的规则和模板
├── agents/          # 🤖 Agent 层 — 每个角色的身份文档
├── skills/          # 🔧 Skill 层 — 可执行的标准化能力
└── memory/          # 🧠 记忆层 — 持续进化的知识资产
```

**11 个 Agent**，覆盖团队所有角色：

| 角色 | 文件 | 核心职责 |
| --- | --- | --- |
| Knowledge Curator | knowledge-curator.md | 知识守门人，自动审查沉淀 |
| CTO | cto.md | 技术战略、商务拓展、客户需求转技术 |
| 架构师 | architect.md | 方案评审、架构设计、技术创新探索 |
| 部门总监 | director.md | 团队管理、项目管控、运营会议 |
| 后端工程师 | backend-engineer.md | 编码、接口设计、代码审查 |
| 前端工程师 | frontend-engineer.md | 页面开发、组件设计、性能优化 |
| QA 工程师 | qa-engineer.md | 测试用例、缺陷跟踪、质量报告 |
| DevOps 工程师 | devops-engineer.md | 部署、监控、CI/CD |
| 需求分析师 BA | ba-analyst.md | 需求收集、文档输出、用户故事 |
| UI 设计师 | ui-designer.md | 视觉规范、设计评审、走查 |
| PM/PMO | pm-pmo.md | 项目计划、进度跟踪、风险管理 |

**18 个 Skill**，覆盖所有高频重复工作：

技术选型、架构评审、代码审查、接口文档、测试用例、部署清单、会议纪要、项目成本核算、周报生成、商务方案、需求分析、用户故事、SQL 优化、前端性能分析、缺陷分析、新技术研究、UI 规范文档……

**但这套系统最关键的不是这 11 个 Agent 和 18 个 Skill。**

最关键的是第四层：**memory（记忆层）**。

以及一个专门的角色：**Knowledge Curator（知识守门人）**。

## 三、为什么大多数 AI Agent 系统用着用着就废了

原因只有一个：**它是静态的。**

你第一天搭好了框架。第 30 天，框架还是那个框架。

你积累了经验，框架不知道。
你调整了标准，框架不更新。
你发现了更好的模板，框架不记得。

最后的结果是：你开始绕过系统，直接跟 AI 说话。系统成了摆设。

**真正能持续使用的系统，必须会自己进化。**

这套系统的进化机制是这样运转的：

```
任意 Agent 完成一次工作
        ↓
自动判断：这次有没有新经验值得沉淀？
        ↓
有 → 生成「知识提案」→ 写入待审目录
        ↓
Knowledge Curator 自动审查
（判断：是全局的还是专属的？是真知识还是一次性特殊情况？）
        ↓
审查通过 → 写入对应记忆文件 → 通知你
审查拒绝 → 静默归档，不打扰你
        ↓
你看到通知：认可就不管，不认可就手动删除
```

你不需要维护系统。系统在维护自己。

## 四、三层记忆架构：知识不再是一堆文件

第一代 Agent 系统的通病：记忆库是个文件夹，扔进去，找不到，慢慢就不扔了。

这套系统的记忆分三层：

```
memory/
├── proposals/          # 待审区：Agent 提交的知识提案
│   └── archived/       # 已处理归档
├── shared/
│   └── learnings.md    # 全局迭代记录（影响所有 Agent）
└── agents/             # 每个 Agent 的私有记忆
    ├── cto/
    │   ├── learnings.md     # CTO 角色的经验积累
    │   └── templates/       # CTO 积累的专属模板
    ├── architect/
    └── ...（每个角色都有）
```

**全局记忆**：3 个以上角色都用到的经验，提升到

```
shared/
```

，影响所有人。

**专属记忆**：只有某个角色会用到的，沉淀到那个角色自己的

```
learnings.md
```

。

**提案待审区**：任何知识在写入之前，必须经过 Knowledge Curator 审查。防止垃圾知识污染系统。

---

## 五、Knowledge Curator：系统里最重要的角色

很多人搭 Agent 系统，Agent 越来越多，知识越来越乱。

根本原因是：**没有守门人。**

Knowledge Curator 就是这个守门人。它的审查标准是：

**通过条件**（满足任意一条）：

- 用户明确提供了新的模板、格式或规则要求
- 同类场景已出现 2 次以上且有规律可循
- 发现的经验能显著提升其他 Agent 的输出质量

**拒绝条件**（满足任意一条）：

- 本次任务是明确的一次性特殊场景
- 提案内容与已有记录高度重复
- 提案表述模糊，无法被其他 Agent 复用

**拒绝时静默处理，通过时才通知你。**

你只需要在系统通知你「已更新」时，看一眼觉得不对就删掉。

其他时间，你完全不用管。

## 六、每个 Agent 的解剖：以 CTO 为例

每个 Agent 文档的结构是统一的：

```
# CTO Agent

## 加载顺序
（先读全局规则，再读全局记忆，再读自己的记忆，最后读本文件）

## 身份定位
（是谁、职责边界、决策权限）

## 核心职能与对应 Skills
（触发什么场景 → 调用哪个 Skill）

## 工作流程（SOP）
（每种场景的标准步骤，步骤化、可执行）

## 输入 / 输出规范
（接收什么 → 输出什么）

## 协作关系
（上游是谁 → 下游是谁）

## 知识沉淀触发规则
（完成工作后的自检清单，判断是否需要提案）
```

CTO Agent 的职能对应 4 个 Skill：

```
客户来了需求
    ↓
business-proposal Skill → 技术商务方案
tech-selection Skill    → 技术路线建议
    ↓
内部评审（architect Agent 参与）
    ↓
对外交付
```

架构师 Agent 有 5 个评审维度，每个都有具体检查项：

```
可扩展性 / 可维护性 / 安全性 / 性能 / 可观测性

不是「这个方案有没有问题」
是「这 23 个检查项，逐条过」
```

这就是 Agent 和「随便问 AI」的区别：**有标准，有流程，有记忆。**

## 七、全局层：每个 Agent 都要遵守的规则

```
shared/
```

 目录下有三个全局文件，所有 Agent 加载时必须先读：

**GLOBAL\_RULES.md** — 最高优先级规则

- 准确优先：禁止编造数据
- 可追溯：输出必须注明来源
- 知识沉淀：每次工作后主动判断是否提案
- 禁止跳过评审直接进入实施

**GLOBAL\_TEMPLATES.md** — 通用模板库

- T-001 文档头部模板
- T-002 会议纪要模板
- T-003 技术方案模板
- T-004 风险登记模板
- T-005 知识提案模板

**GLOBAL\_GLOSSARY.md** — 公司术语表
统一「缺陷」还是「Bug」，统一「迭代」还是「Sprint」，统一「接口」还是「API」。

术语不统一，是跨团队沟通最隐形的成本。

## 八、Skill 的设计哲学：能被机器执行的标准

每个 Skill 都遵循 Claude 的 SKILL.md 规范：

```
skill-name/
├── SKILL.md          # 触发条件、工作流程、输出模板
└── scripts/          # 可执行的 Python 脚本（本地可运行）
```

举个例子，

```
code-review
```

 Skill 的检查维度：

```
逻辑正确性：边界条件是否处理？
异常处理：外部调用是否有 try-catch？
安全性：SQL 是否参数化查询？
性能：是否有 N+1 查询？
可读性：函数长度是否合理？
```

每一条都是「可以被机器执行的判断」，不是「感觉」。

```
deploy-checklist
```

 Skill 更直接：

```
上线前的 12 项强制检查

全部通过 → 可以上线
任意未通过 → 暂停上线
```

再也不会因为「以为检查过了」而出现线上事故。

## 九、这套系统解决的是什么问题

不是「让 AI 替我干活」。

是「让标准不再活在人的脑子里」。

**以前**：

- 技术选型的对比维度，在架构师的脑子里
- 代码审查的检查清单，在高级工程师的经验里
- 上线的注意事项，在 DevOps 的肌肉记忆里

**人一走，知识就走了。**

**现在**：

- 技术选型怎么比 →

  ```
  tech-selection
  ```

   Skill 里写清楚了
- 代码审查看什么 →

  ```
  code-review
  ```

   Skill 里列明了
- 上线前检查什么 →

  ```
  deploy-checklist
  ```

   Skill 里强制执行

**人走了，系统还在。而且系统会越用越好。**

## 十一、这套系统的边界

我需要说清楚它做不了什么。

**它不能替代真正的技术判断。**
架构评审 Skill 给出的是检查清单，不是结论。结论还是需要有经验的人来做。

**它不能替代人与人之间的信任。**
PM Agent 可以输出项目周报，但跨团队的优先级博弈，是人的问题。

**它需要你先把标准说清楚。**
系统只能执行你定义的标准。如果你自己都不知道代码审查该看什么，Agent 也不会知道。

**它是一套起点，不是终点。**
第一版的知识都是框架性的，随着你实际使用，memory 层会不断积累你们公司特有的经验和规律。三个月后的系统，和第一天相比，应该完全不同。

## 十二、一句话总结

**你的团队，不应该每次都从零开始。**

每一次技术选型的对比逻辑，每一次架构评审发现的风险模式，每一次上线事故总结的教训——

这些经验应该沉淀在系统里，而不是消失在会议室里。

搭这套系统花了我两周。

之后每次用，系统都在变好。

我什么都不用做。
