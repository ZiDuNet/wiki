> 你和AI编程高手之间，可能只差一个Skill

## 写在前面

每次让AI写代码，都要重复解释"我们项目的规范是……"？

AI写出来的代码总差点意思，反复改3-4次才能用？

明明上次调教好了，换个对话窗口又打回原形？

**问题不在AI，在于你没给它写Skill。**

Skill就是AI编程助手的"工作手册"——告诉它遇到什么情况该怎么做。写好Skill，AI就像熟悉你项目规范的老搭档；不写Skill，AI就是每次都要从头培训的新人。

## 一、Skill到底是什么？

**Skill = 一份结构化的"最佳实践文档"，让AI在特定场景下自动遵循你定义的工作方式。**

| 没有 Skill | 有 Skill |
| --- | --- |
| 每次告诉AI"测试要写在前头" | AI自动先写测试再写代码 |
| 每次提醒"别用any类型" | AI自动避开any，用具体类型 |
| 每次手动检查安全漏洞 | AI写完自动做安全审查 |

**核心价值：把你的经验变成AI的"肌肉记忆"。**

## 二、Skill长什么样？

一个Skill就是一个Markdown文件：

```
---name: my-skill-namedescription: Use when 遇到什么情况时使用这个skill---# Skill名称## 概述一句话说清楚核心原则。## 什么时候用- 场景1- 场景2## 核心规则1. 规则12. 规则2## 怎么做具体步骤和代码示例## 常见错误- 错误1：描述 + 正确做法
```

**没有复杂配置，就是一份纯文本文档。**

## 三、5步写出一个好Skill

### 第1步：找到痛点

**"AI在哪件事上反复让我不满意？"**

痛点信号：每次手动纠正同一问题 / AI总漏掉某步骤 / 你在不同对话中重复说同样的话

### 第2步：先测试"没有Skill时AI的表现"

故意不提要求，让AI完成任务，记录它"自然状态下"怎么做。比如写"先写测试"的Skill，先看AI是不是直接写代码，记录它的借口——"太简单不需要测试""先写完再补"。

**不知道AI会犯什么错，就写不出有效的规则。**

### 第3步：写Skill内容

5个要点：

**1. 描述写"什么时候用"，不写"做了什么"**

```
# 错误description: 先写测试再写代码，确保TDD流程# 正确description: Use when 实现任何新功能或修复bug，在写实现代码之前
```

AI根据描述判断"该不该用这个Skill"。写"做了什么"，AI可能不去读完整内容。

**2. 规则要具体，不要抽象**

```
# 错误：遵循最佳实践 / 代码要写好# 正确：写任何功能前，先写一个失败的测试 / 测试失败后，再写最小实现让它通过
```

**3. 堵住AI的"借口"**

```
## 铁律写代码前必须先写测试。**没有任何例外：**- "这个功能太简单" → 简单的代码也需要测试- "我先写完再补测试" → 先写测试和后写测试是两回事- "时间紧来不及" → 写测试比修bug更快
```

**4. 一个优秀示例胜过十个平庸示例**

不要JavaScript/Python/Go各写一遍。一个完整示例就够了。

**5. 控制篇幅**

| Skill类型 | 建议字数 |
| --- | --- |
| 常驻加载 | < 200词 |
| 一般 | < 500词 |
| 带参考文档 | SKILL.md < 500词，参考文档放单独文件 |

### 第4步：测试Skill是否生效

带上Skill让AI完成任务，看是否遵循规则。没遵循就补规则，循环验证。

### 第5步：持续迭代

AI找新借口了？加反借口规则。规则有漏洞？补上。

## 四、用skill-creator自动创建

Claude Code 内置了 skill-creator 工具，直接说：

```
帮我创建一个 Skill，用于 [你的需求描述]
```

它会走这个流程：

1

意图捕获 — 了解你想让Skill做什么

2

调研访谈 — 澄清边缘情况和成功标准

3

生成草稿 — 自动写出SKILL.md

4

跑测试用例 — 对比"有Skill"和"没Skill"的效果

5

人工评审 — 你查看结果，留下反馈

6

迭代改进 — 根据反馈修改，循环直到满意

**手动 vs skill-creator：**

| 场景 | 推荐方式 |
| --- | --- |
| 简单规则型Skill（几条规则） | 手动写，更快 |
| 复杂工作流Skill | skill-creator，自带测试验证 |
| 快速验证想法 | 手动写草稿，后续用 skill-creator 优化 |

skill-creator 还能自动优化 

```
description
```

 字段的触发准确率——生成20个测试查询，跑触发率，迭代出最优描述。

## 五、Skill的目录结构

**最小结构**（一个文件就够）：

```
my-skill/└── SKILL.md
```

**标准结构**（内容较多时）：

```
my-skill/├── SKILL.md              # 主文件（必须）├── scripts/              # 可执行脚本（确定性操作）├── references/           # 参考文档（按需加载）└── assets/               # 输出资源（模板、图标，不加载到上下文）
```

**三级加载机制：**

| 层级 | 何时加载 | 大小建议 |
| --- | --- | --- |
| 元数据（name + description） | 始终在上下文 | ~100词 |
| SKILL.md 正文 | Skill被触发时 | < 500行 |
| references/scripts/assets | 按需读取 | 无限制 |

**关键原则：** SKILL.md 保持精简，详细内容放 references/，注明"需要时读取 xxx.md"

多框架时按变体组织：

```
references/aws.md
```

、

```
references/gcp.md
```

，AI只读当前需要的。

## 六、Frontmatter字段详解

**只有 

```
name
```

 和 

```
description
```

 是必填的**，其他都可选。

```
---name: my-skill-name           # 必填：小写字母+连字符，与目录名一致description: Use when ...     # 必填：触发条件，建议以"Use when"开头allowed-tools: Read, Bash     # 可选：限制可用工具，支持 Bash(gh *) 约束context: fork                 # 可选：在子代理中隔离运行agent: Explore                # 可选：指定代理类型disable-model-invocation: true  # 可选：只能用户 /skill-name 手动触发user-invocable: false         # 可选：只能AI自动触发---
```

## 七、2个真实案例

### 案例1：代码审查Skill

```
---name: code-review-checklistdescription: Use when 完成任何代码编写后，在提交之前自动审查---# 代码审查清单## 铁律写完代码必须审查，没有任何例外。## 审查项1. **安全**：硬编码密钥？SQL注入？XSS？2. **错误处理**：外部调用都有错误处理吗？3. **类型安全**：有没有用any？4. **命名**：变量和函数名能表达意图吗？5. **重复**：有可以提取的重复逻辑吗？## 常见问题- "只是小改动" → 小改动引入的bug最致命- "手动测试过了" → 手动测试不保证边界情况
```

### 案例2：调试Skill

```
---name: systematic-debuggingdescription: Use when 遇到任何bug、测试失败或异常行为，在尝试修复之前---# 系统性调试## 铁律**没有找到根因之前，不允许提修复方案。**## 四步流程1. **根因调查**：读错误信息 → 复现 → 查最近变更 → 追踪数据流2. **模式分析**：找正常代码 → 对比差异 → 列出所有不同点3. **假设验证**：提具体假设 → 最小改动验证 → 一次只改一个变量4. **实施修复**：先写失败测试 → 修复根因 → 验证通过## 危险信号- "先试试改这个" → 你在猜，不是在调试- 连续3次修复失败 → 问题可能在架构层面
```

## 九、3个最容易踩的坑

**坑1：写流水账** → Skill是规则手册，写"做什么"，不写"我经历了什么"

**坑2：规则太模糊** → "代码要健壮"没用，"所有外部API调用必须有超时设置（默认5秒）"才有用

**坑3：描述里写了流程** → 描述只写"什么时候用"，流程写在正文。AI读到描述就"自以为懂了"，不会去读完整内容
